# Код-ревью (Code Review): обзор

## Зачем нужно код-ревью

Код-ревью — процесс проверки изменений кода другими членами команды перед их слиянием в основную ветку. Цели:

- найти дефекты и архитектурные проблемы до релиза;
- поддерживать единый стиль и качество кода;
- распространять знания о кодовой базе среди команды (knowledge sharing);
- наставничество и обмен опытом между разработчиками.

## Процесс через Pull Request / Merge Request

1. Разработчик создаёт ветку (feature branch) и вносит изменения.
2. Открывается Pull Request (PR) / Merge Request (MR) с описанием изменений.
3. CI автоматически прогоняет тесты, линтеры, проверки безопасности.
4. Один или несколько ревьюеров оставляют комментарии, запрашивают изменения (request changes) или одобряют (approve).
5. После одобрения и прохождения проверок PR сливается (merge) в основную ветку.

## На что обращать внимание при ревью

- **Корректность** — решает ли код поставленную задачу, есть ли edge cases.
- **Читаемость** — понятны ли имена переменных/функций, нет ли излишней сложности.
- **Тесты** — покрыты ли новые сценарии тестами.
- **Безопасность** — нет ли утечки секретов, SQL-инъекций, небезопасной обработки пользовательского ввода.
- **Архитектура** — соответствует ли решение принятым паттернам проекта, нет ли дублирования.
- **Производительность** — нет ли очевидных проблем (N+1 запросы к БД, неэффективные алгоритмы).

## Этикет код-ревью

- Комментарии должны касаться кода, а не личности автора.
- Разделяйте блокирующие замечания ("must fix") и предложения ("nit", "nice to have").
- Ревью должно быть своевременным — затянутые ревью замедляют всю команду.
- Автор PR не должен воспринимать замечания как критику — это часть совместной работы над качеством.

## Конвенциональные коммиты (Conventional Commits)

Соглашение об именовании коммитов вида `<тип>(<область>): <описание>`, например:
- `feat(rag): добавить историю диалога в промпт`
- `fix(priority-areas): исправить переполнение varchar(255)`
- `docs(readme): обновить инструкцию по запуску`

Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci`. Это упрощает автоматическую генерацию changelog и определение версии релиза.
