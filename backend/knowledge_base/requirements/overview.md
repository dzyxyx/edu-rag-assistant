# Инженерия требований (Requirements Engineering): обзор

## Что такое требование

Требование — это документированная потребность относительно того, что должна делать конкретная система или продукт, либо какими свойствами она должна обладать.

## Виды требований

- **Бизнес-требования (Business requirements)** — цели заказчика/компании, описывают, зачем нужен продукт.
- **Требования пользователей (User requirements)** — задачи, которые пользователь должен решать с помощью системы (часто оформляются как user stories или use cases).
- **Функциональные требования (Functional requirements)** — что система должна делать: конкретное поведение, функции, расчёты.
- **Нефункциональные требования (Non-functional requirements, NFR)** — атрибуты качества: производительность, безопасность, надёжность, удобство использования, масштабируемость.

## Процесс работы с требованиями

1. **Elicitation (сбор/выявление)** — интервью, опросы, наблюдение, анализ документов, воркшопы.
2. **Analysis (анализ)** — приоритизация, разрешение конфликтов, моделирование (диаграммы, прототипы).
3. **Specification (документирование)** — оформление в виде user stories, use cases, спецификаций (SRS).
4. **Validation (проверка)** — подтверждение с заинтересованными сторонами, что требования верны и полны.
5. **Management (управление изменениями)** — трассируемость, версионирование, контроль изменений.

## User Story

Стандартный формат: «Как `<роль>`, я хочу `<действие>`, чтобы `<ценность/цель>`».

Критерии качества user story — мнемоника **INVEST**:
- **I**ndependent — независима от других историй
- **N**egotiable — может обсуждаться и уточняться
- **V**aluable — приносит ценность пользователю/заказчику
- **E**stimable — может быть оценена командой
- **S**mall — достаточно мала для выполнения за спринт
- **T**estable — есть критерии приемки, по которым можно проверить выполнение

## Критерии приёмки (Acceptance Criteria)

Условия, при выполнении которых история считается завершённой. Часто оформляются в формате Given/When/Then (Gherkin):

```
Given <начальное состояние>
When <действие пользователя>
Then <ожидаемый результат>
```

## Типичные ошибки при работе с требованиями

- Смешивание решения (как делать) и требования (что нужно)
- Неоднозначные формулировки ("система должна быть быстрой" без метрик)
- Отсутствие трассируемости между требованиями, задачами и тестами
- Игнорирование нефункциональных требований до конца проекта
