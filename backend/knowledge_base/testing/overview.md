# Тестирование программного обеспечения: обзор

## Цели тестирования

Тестирование — процесс проверки соответствия программного продукта требованиям и выявления дефектов до того, как они дойдут до пользователя. Тестирование не доказывает отсутствие ошибок — оно повышает уверенность в качестве продукта.

## Уровни тестирования

- **Unit-тесты (модульные)** — проверяют отдельные функции/классы в изоляции. Быстрые, дешёвые, пишутся разработчиками.
- **Интеграционные тесты** — проверяют взаимодействие между модулями/сервисами (например, API + база данных).
- **Системные тесты (System testing)** — проверка системы целиком на соответствие требованиям.
- **Приёмочные тесты (Acceptance testing)** — проверка готовности продукта к передаче заказчику/пользователю (UAT — User Acceptance Testing).

## Пирамида тестирования

Классическая пирамида тестирования рекомендует:
- много быстрых unit-тестов в основании,
- среднее количество интеграционных тестов,
- немного дорогих end-to-end (E2E) тестов на вершине.

Это снижает время прогона тестов и упрощает локализацию дефектов.

## Виды тестирования по подходу

- **Функциональное тестирование** — проверка соответствия функциональным требованиям.
- **Нефункциональное тестирование** — производительность (performance/load testing), безопасность (security testing), удобство использования (usability).
- **Регрессионное тестирование** — повторный прогон тестов после изменений, чтобы убедиться, что старая функциональность не сломалась.
- **Смоук-тестирование (smoke testing)** — быстрая проверка базовой работоспособности после деплоя.
- **Тестирование "чёрного ящика"** — без знания внутренней реализации, на основе требований.
- **Тестирование "белого ящика"** — с учётом структуры кода (покрытие путей выполнения).

## TDD и BDD

- **TDD (Test-Driven Development)** — сначала пишется тест (он падает), затем минимальный код, чтобы тест прошёл, затем рефакторинг. Цикл "red-green-refactor".
- **BDD (Behavior-Driven Development)** — сценарии описываются на языке, понятном бизнесу (Given/When/Then), часто с помощью инструментов типа Cucumber/Gherkin.

## CI и тестирование

Автоматические тесты обычно запускаются в CI-пайплайне при каждом push/pull request: это позволяет находить регрессии рано и не допускать слияния "красного" кода в основную ветку (см. раздел DevOps/CI-CD).
