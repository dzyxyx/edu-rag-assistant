# Практики тестирования: метрики и инструменты

## Покрытие кода (Code Coverage)

Метрика, показывающая, какой процент кода выполняется во время прогона тестов (строки, ветвления, функции). Высокое покрытие не гарантирует отсутствие ошибок, но низкое покрытие — сигнал о непроверенных участках кода.

Распространённые виды:
- **Line coverage** — доля выполненных строк кода.
- **Branch coverage** — доля выполненных веток условий (if/else).

## Тест-кейс и тест-план

- **Тест-кейс** — описание конкретной проверки: предусловия, шаги, входные данные, ожидаемый результат.
- **Тест-план** — документ, описывающий объём, подход, ресурсы и график тестирования для проекта или релиза.

## Дефекты (баги) и их жизненный цикл

Типичные статусы дефекта: New → Assigned → In Progress → Fixed → Retest → Closed (или Reopened, если исправление не сработало).

Важные атрибуты дефекта: severity (критичность для системы), priority (срочность исправления), шаги воспроизведения, окружение.

## Инструменты тестирования (примеры)

- **Python**: pytest, unittest, hypothesis (property-based testing)
- **JavaScript/TypeScript**: Jest, Vitest, Playwright, Cypress (E2E)
- **API-тестирование**: Postman, httpx + pytest, REST Assured
- **Нагрузочное тестирование**: JMeter, Locust, k6

## Mock, Stub, Fake

При unit-тестировании внешние зависимости (БД, API, очереди) часто заменяются:
- **Stub** — возвращает заранее заданные ответы.
- **Mock** — то же самое, но дополнительно проверяет, что метод был вызван с ожидаемыми аргументами нужное число раз.
- **Fake** — упрощённая, но рабочая реализация (например, in-memory база данных вместо реальной).

В этом проекте, например, режим `MOCK_LLM=true` заменяет реальную LLM (Ollama) на простую функцию-заглушку — это позволяет разрабатывать и тестировать API без тяжёлой модели.
